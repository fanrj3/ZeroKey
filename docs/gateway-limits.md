# 网关限额与迁移

随附的 `config.yaml` 不再设置 `upperbound_key_generate_params.tpm_limit`。项目的模型范围、每日费用预算与有效期继续由授权流程控制。上游服务的账户、分组、模型和并发限制仍以来源配置为准。

旧模板中的 `tpm_limit: 100000` 会被 LiteLLM 1.109.0 作为未显式提供 TPM 时的签发默认值，存入虚拟 Key。它既限制可填写的上限，也会补齐空值。仅编辑配置文件不能移除已存入数据库的限制，重启桌面程序也不会修改独立部署的网关。

迁移已有网关时分别处理两件事：

1. 在 LiteLLM 管理后台将对应 ZeroKey 项目的 Key TPM 清空。管理员 API 等价操作为 `POST /key/update`，请求中明确发送 `tpm_limit: null`；省略字段表示保留旧值。更新后读取 `/key/info`，确认 TPM 为 null，并核对模型、每日预算和有效期。使用已有管理员凭证，不在对话中复制 Key。
2. 删除配置中的固定 TPM 上限，并在没有正在运行的请求时重新加载 LiteLLM，使新签发默认值生效。这一版本不能通过常规安全配置热更新刷新该复杂参数。现有 Key 的在线更新不需要重启网关。

当前模板仍保留独立的 60 RPM 签发上界。请求数与 token 吞吐是两种不同限制；取消 TPM 不等于修改 RPM，也不代表取消上游限制。

排查 429 时先确认限流层级。LiteLLM 本地 Key 的 `ProxyRateLimitError` 与来源返回的 429 分开处理。并行请求的预留量包含估算输入和输出上限，不能只用已生成的 token 判断是否还有额度。LiteLLM 1.109.0 的该本地限流实现返回固定窗口长度的 `retry-after`；它不能保证等待后一定有足够额度。
